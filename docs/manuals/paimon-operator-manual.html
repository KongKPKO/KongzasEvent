ขอบเขตการดูแล

แยกหน้าที่ให้ชัดเจน

  1. เจ้าของร้านและทีมดูแลสินค้า อีเวนต์ คิว และออเดอร์ของร้านตามสิทธิ์ที่ได้รับ ส่วน Platform Admin ดูแลบัญชีและเรื่องระดับแพลตฟอร์ม
  2. ระบบประกอบด้วยหน้าเว็บบน Firebase Hosting และบริการ Auth, Database, Storage และ Edge Functions ของ Supabase ตรวจสภาพแวดล้อมก่อนทำงานทุกครั้ง
  3. DEV ใช้สำหรับข้อมูลทดสอบ ส่วน PROD มีข้อมูลผู้ใช้จริง อย่านำข้อมูลจริงไปสร้างเป็นตัวอย่างหรือส่งผ่านช่องทางสาธารณะ

เข้าหน้า Platform Admin

เข้าใช้งานอย่างปลอดภัย

  1. เปิด /admin บนเว็บไซต์ของสภาพแวดล้อมที่ตั้งใจ แล้วเข้าสู่ระบบด้วยบัญชีที่ได้รับสิทธิ์ Platform Admin
  2. สิทธิ์เจ้าของร้านเพียงอย่างเดียวไม่เพียงพอ ผู้ดูแลต้องลงทะเบียนหรือยืนยัน MFA ตามขั้นตอนที่ระบบแสดง
  3. หากทำอุปกรณ์ MFA สูญหาย ให้ยืนยันตัวตนนอกระบบก่อนให้ผู้มีสิทธิ์จัดการปัจจัยยืนยันและบังคับลงทะเบียนใหม่ ห้ามส่งรหัสผ่านหรือรหัส OTP

ตรวจความพร้อมก่อนใช้งาน

ตรวจบริการและเส้นทางหลัก

  1. เปิดหน้าเว็บ เข้าระบบด้วยบัญชีทดสอบที่ได้รับอนุญาต และตรวจว่าร้าน อีเวนต์ และออเดอร์เปิดได้
  2. ตรวจสถานะ Auth, Database, Storage, Edge Functions และการส่งอีเมลในสภาพแวดล้อมที่เกี่ยวข้อง
  3. ตรวจสิทธิ์ทีมและข้อมูลติดต่อของร้าน รวมถึงวันที่ เขตเวลา ช่วงขาย วิธีรับเงิน และการส่งมอบก่อนเปิดขาย

รับเรื่องและติดตามปัญหา

เริ่มจากข้อมูลที่จำเป็น

  1. บันทึกเวลาและเขตเวลา หน้าที่พบปัญหา ขั้นตอนก่อนเกิดเหตุ อุปกรณ์ และรหัสออเดอร์หรือคิวเมื่อจำเป็น
  2. ตรวจสถานะออเดอร์ การชำระ และการส่งมอบแยกกัน ตรวจยอดกับบัญชีธนาคารจริงก่อนแนะนำการยืนยันชำระ
  3. ขอรายละเอียดผ่านช่องทางส่วนตัว ห้ามขอรหัสผ่าน OTP หรือเผยแพร่สลิปและข้อมูลลูกค้า

คิว อีเวนต์ และสต็อก

ตรวจบริบทก่อนทำรายการ

  1. ตรวจอีเวนต์ที่กำลังให้บริการก่อนเปิดหน้าคิวหรือขายหน้าบูธ ร้านสามารถเปิดแผงจัดการคิวจาก POS หรือใช้หน้าคิวแบบเต็มได้
  2. สินค้าในคลังต้องจัดสรรให้ช่องทางขายก่อน สินค้าอีเวนต์ที่ซ่อนยังคงกันสต็อกไว้ หากต้องการคืนส่วนที่ไม่ได้ใช้ให้ลดจำนวนจัดสรร
  3. ช่วงขายที่สิ้นสุดแล้วเปิดใหม่ไม่ได้ หลังงานจบอนุญาตขยายเวลาปิดเฉพาะช่วงขายหลังงานที่ยังเปิดอยู่

ก่อนและหลังปล่อยระบบ

Local → DEV → PROD

  1. ทบทวน source, migration, Edge Functions และเป้าหมาย hosting ของแต่ละ environment ก่อนเริ่ม ตรวจผลทดสอบและการสำรองข้อมูลตามขั้นตอนที่องค์กรใช้อยู่
  2. ใช้ migration dry run ตรวจรายการก่อนนำฐานข้อมูลขึ้น PROD จากนั้น deploy frontend ที่ build ด้วยค่าของ PROD และตรวจ response กับ flow สำคัญ
  3. บันทึก commit, เวลา deploy และผลตรวจ เตรียมวิธีคืน frontend หรือแก้ไขไปข้างหน้า การคืน frontend ไม่ได้ย้อนรายการขายหรือ schema โดยอัตโนมัติ

สำรองและกู้คืน

ตรวจว่าสำรองได้จริง

  1. ตรวจแผนสำรองปัจจุบันของฐานข้อมูล ไฟล์ Storage การตั้งค่า และความลับกับผู้ดูแลบริการ อย่าสมมติว่ามี automatic backup
  2. บันทึกเวลา ขอบเขต และตำแหน่งสำรอง พร้อมทดลองกู้คืนในสภาพแวดล้อมแยกเป็นระยะ
  3. ก่อนกู้คืนหรือเปลี่ยนข้อมูลจริง ให้ประเมินผลกระทบและรับอนุมัติการดำเนินการกับเป้าหมายที่ชัดเจน
