# NireQ Production Readiness Spec v1

วันที่ 12 กันยายน 2026 — TOR, ขอบเขตผลิตภัณฑ์, UX และเกณฑ์ตรวจรับในเอกสารเดียว

สถานะ: สเปกพร้อมใช้วางแผนพัฒนา ยึดการตัดสินใจของเจ้าของผลิตภัณฑ์ในบทสนทนา การมีสเปกหรือภาพต้นแบบไม่ใช่การรับรองว่า implementation ผ่านตรวจรับแล้ว รอบนี้ไม่มีการแก้ระบบหรือ deploy

## 1. เป้าหมายและขอบเขต

NireQ ช่วยครีเอเตอร์ ศิลปิน คอสเพลเยอร์ circle และร้านเล็กจัดการการออกบูธ คิว การขาย สินค้า และการขายออนไลน์ พร้อมเก็บข้อมูลการดำเนินงานเพื่อเรียนรู้จากงานที่ผ่านมา

- v1 เปิดสมัครและเริ่มใช้งานเอง ไม่ต้องรออนุมัติร้าน ใช้กระบวนการยืนยันตัวตนที่เหมาะสมของระบบ
- ฟีเจอร์ v1 ใช้ฟรีทั้งหมด ไม่มีระบบเรียกเก็บค่าบริการในรอบนี้
- รองรับเว็บคอมพิวเตอร์ มือถือ แท็บเล็ต และการติดตั้ง PWA
- รวม Queue, POS, Product/Variant/SKU/Stock, Team, Event Pre/Post-order, Online Campaign, Promotion, Payment review, Pickup/Shipping และรายงานเดิม
- ต้องขายและเรียกคิวต่อได้เมื่อเครื่องขายขาดการเชื่อมต่อ ตามข้อจำกัดและเกณฑ์ในหัวข้อออฟไลน์
- คงกติกาที่ทำแล้วและมีประโยชน์ ตรวจหลักฐานก่อนเปลี่ยน ไม่สร้างฟีเจอร์เดิมซ้ำ

นอกขอบเขต v1: App Store/Google Play, แอป native ใหม่, subscription, การวิเคราะห์คาดการณ์ขั้นสูง, ระบบจัดซื้อ/ผู้ขายวัตถุดิบ, แชทบริการลูกค้าในระบบ และการยืนยันตัวบุคคลเข้มงวดเพื่อจำกัดการซื้อข้ามออเดอร์ การคิดราคาแพ็กเกจในบทสนทนาเป็นแนวคิดที่พักไว้ ไม่ใช่ราคาตกลง

## 3. สิทธิ์และขอบเขตข้อมูล

| การกระทำ | Owner | Manager | Seller | Queue staff |
|---|---|---|---|---|
| ขายผ่าน POS | ได้ | ได้ | ได้ | ไม่ได้ |
| เรียก/จัดการคิวออนไลน์ตาม event ที่มีสิทธิ์ | ได้ | ได้ | ได้ | ได้ |
| ขายและเรียกคิวออฟไลน์บนเครื่องหลัก | ได้ | ได้ | ได้ | ไม่ได้ |
| เพิ่ม/แก้สินค้า รับสินค้าเพิ่ม แก้ยอดสต็อก | ได้ | ได้ | ไม่ได้ | ไม่ได้ |
| เชิญ/ถอด Seller และ Queue staff | ได้ | ได้ | ไม่ได้ | ไม่ได้ |
| แต่งตั้ง/ถอด Manager | ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| เปลี่ยน/ถอด Owner | ไม่เพิ่ม flow นี้ในงานนี้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |

การคืนเงิน ตรวจสลิป เปลี่ยนบทบาทระหว่าง Seller/Queue staff และสิทธิ์เฉพาะอื่นที่ไม่อยู่ในตาราง ให้ตรวจ enforcement เดิมก่อนขยาย ไม่ตีความว่า manager ทำทุกอย่างเท่า owner โดยอัตโนมัติ

ที่อยู่และช่องทางติดต่อจัดส่งให้ Owner, Manager และผู้รับผิดชอบจัดส่งที่ได้รับสิทธิ์เท่านั้น Queue staff เห็นเฉพาะข้อมูลจำเป็นต่อเรียกคิวและ pickup การเป็น Seller ไม่ให้สิทธิ์ดูที่อยู่ทั้งหมดโดยอัตโนมัติ ต้องกำหนดจากงาน fulfillment ที่รับผิดชอบ

เกณฑ์ตรวจรับ: บังคับที่ฐานข้อมูล/API ไม่ใช่ซ่อนปุ่ม; ทดสอบข้ามร้าน ข้าม event เรียก API ตรง บัญชีถูกถอด และการยกระดับสิทธิ์ผ่าน invitation; ข้อมูลสำคัญไม่หลุดไป client ที่ไม่มีสิทธิ์

## 4. สินค้าและสต็อก

ใช้ส่วนจัดการเดิม แต่แยกการกระทำให้เข้าใจได้:

1. รับสินค้าเพิ่ม: ระบุจำนวนที่ได้รับจริง บันทึกเหตุผลรับสินค้าเข้าอัตโนมัติ หมายเหตุไม่บังคับ ไม่ต้องสร้าง purchase order
2. แก้ไขยอดสต็อก: เพิ่มหรือลดเพื่อแก้ความคลาดเคลื่อน ต้องระบุเหตุผล เช่น ของเสีย ของหาย ตรวจนับ
3. จัดสรรไป Event/Campaign หรือคืน allocation: แยกจากรับสินค้าทางกายภาพ ไม่สร้างสต็อกขึ้นใหม่

ทั้งรับเพิ่มและแก้ยอดต้องบันทึกผู้ทำ เวลา จำนวนเปลี่ยน ก่อน/หลัง เหตุผล และสินค้าที่เกี่ยวข้องอย่างตรวจย้อนหลังได้ การ retry ต้องไม่เพิ่ม/ลดซ้ำ และประวัติต้องผูกกับการเปลี่ยนจำนวนจริงในธุรกรรมเดียวกัน

รักษากติกา PRODUCT.md: variant นับแยก; unlimited ไม่เท่ากับ finite; ขายแล้ว จองอยู่ และ allocation ที่ยังไม่ใช้มีความหมายแยกกัน; refund ไม่เท่ากับ restock; ห้ามลด commitment ที่ขาย/จองแล้วเพื่อทำให้หน้าจอตัวเลขสวย

เกณฑ์ตรวจรับ: สต็อกหน้าสรุปกับ checkout ตรงกัน; รับเพิ่ม/แก้ยอด/คืน allocation ไม่ซ้ำ; seller ทำรายการปรับตรงไม่ได้; รายงานวิเคราะห์ไม่เปลี่ยนความหมายตามชื่อสินค้า/โปรโมชั่นที่ถูกแก้ภายหลัง

## 5. ช่องทางขายและการจ่ายเงิน

Online Campaign เป็นรอบขายอิสระจาก Event ใช้ allocation ชัดเจน รองรับสินค้าจำนวนจำกัดและจบรอบเมื่อขายหมด รองรับ shipping หรือนัดรับตามตัวเลือกร้าน ส่วน Event Pre/Post-order ยังคงผูกกับ event ตามเดิม

เพดานซื้อ: ร้านกำหนดต่อสินค้า ต่อ Campaign ต่อออเดอร์ได้ ไม่ตั้งหมายถึงไม่มีเพดานชนิดนี้แต่ยังถูกจำกัดด้วยสต็อก กติกาหนึ่งคนหนึ่งออเดอร์เป็นขอความร่วมมือ ไม่อ้างป้องกันคนเดิมกลับมาซื้อใหม่ได้

กติกาเดิมที่ตรวจพบและใช้ต่อ:

- สร้างออเดอร์ออนไลน์แล้ว hold สินค้าและของแถม finite 15 นาที การใส่ตะกร้าไม่ hold
- เริ่มอัปโหลดก่อน deadline มี technical grace สองนาที ไม่ใช่ให้เริ่มจ่ายหรือเริ่มอัปโหลดปกติหลังหมดเวลา
- ส่งหลักฐานแล้วคง commitment รอร้านตรวจ; หมดเวลาโดยไม่ส่งหลักฐานคืน hold ครั้งเดียว
- ลูกค้าแจ้งโอนแล้วหลังหมดเวลาได้จากหน้าออเดอร์เดิม แต่ไม่คืนสิทธิ์จองให้อัตโนมัติ
- การยอมรับเงินโอนช้าของ Campaign ต้องตรวจสต็อกปัจจุบัน หากไม่พอต้องไม่ยืนยัน และมีเส้นทางจัดการคืนเงิน
- ภาพสลิปไม่ใช่การยืนยันเงินเข้าธนาคารอัตโนมัติ
- ออเดอร์คง snapshot ราคา/โปรโมชั่นขณะสร้าง; การแก้โปรโมชั่นไม่เปลี่ยนยอดย้อนหลัง
- POS วันงานไม่ใช้ timer ชำระเงินออนไลน์ 15 นาที

ตรวจส่วนที่ใช้ร่วมกันระหว่าง Campaign กับ Pre/Post-order ให้ครบ ไม่สรุปว่าโค้ดเฉพาะ Campaign รับรองทุกช่องทางแล้ว

เกณฑ์ตรวจรับ: ผู้ซื้อพร้อมกันซื้อของชิ้นสุดท้ายไม่เกิน stock, เพดานซื้อบังคับ server, retry ไม่สร้าง order/payment ซ้ำ, upload ล้มเหลวมีข้อความและลองใหม่ได้, ปิด Campaign ยังเข้าถึง order lookup และแจ้งเงินโอนช้าได้ตามสิทธิ์

## 6. การทำงานเมื่อเน็ตหลุด — เงื่อนไขสำคัญก่อนเปิดจริง

ความต้องการที่ตกลง: ห้ามบังคับหยุดขายเพียงเพราะเน็ตหลุด; Owner/Manager/Seller ขายและเรียกคิวจากเครื่องขายหลักเครื่องเดียวได้; Queue staff ไม่ทำ queue mutation ออฟไลน์ แต่ช่วยตะโกนเรียก/จัดลำดับหน้างาน

รูปแบบหน้างานเป้าหมาย: หนึ่งเครื่องขายต่อบูธ อาจมีอีกเครื่องสำหรับสตาฟคิว ผู้ใช้ไม่ต้องการขั้นตอนเลือกเครื่องที่ยุ่งยาก อย่างไรก็ตาม “น่าจะใช้เครื่องเดียว” เป็นสมมติฐานการใช้งาน ไม่ใช่กลไกป้องกัน concurrency และยังไม่ได้ตกลงวิธีลงทะเบียนเครื่องหลัก

ข้อกำหนดความถูกต้อง:

- ต้องเตรียมข้อมูลที่จำเป็นและสิทธิ์ใช้งานขณะออนไลน์ก่อนใช้ออฟไลน์ครั้งแรก; ไม่อ้างว่าเครื่องใหม่ที่ไม่เคยโหลดจะทำงานได้
- บันทึกธุรกรรมค้างลงพื้นที่ถาวรในเครื่องก่อนแสดงว่าบันทึกแล้ว พร้อมจำนวนรายการรอส่ง
- ปิด/เปิดแอป รีโหลด สลับแอป และกลับเข้าใช้งานต้องไม่สร้างรายการซ้ำหรือสูญเสียอย่างเงียบ ๆ
- ส่งกลับแบบ idempotent; คำตอบจาก server หายหลังบันทึกสำเร็จต้องตรวจสถานะเดิม ไม่ขายซ้ำ
- สต็อกที่แสดงขณะออฟไลน์เป็นข้อมูลล่าสุดที่เครื่องมี ไม่ใช่คำรับรองยอดรวมปัจจุบัน
- แยกการบันทึกว่าร้านรับชำระแล้วจากการตรวจเงินผ่านระบบออนไลน์ ไม่อ้างตรวจโอนเมื่อเชื่อมต่อไม่ได้
- ขัดแย้งระหว่างเครื่อง ข้อมูลถูกเปลี่ยน หรือสิทธิ์ถูกถอนต้องมีรายการให้ตรวจ ห้ามทิ้งยอดขายจริงหรือฝืนเขียนทับ server
- ไม่ล้าง pending records เมื่อ logout/update โดยไม่มีกระบวนการรักษาข้อมูลและคำอธิบาย

คิวระหว่าง outage:

- ลูกค้ายังรับคิวออนไลน์ได้เมื่อบริการส่วนกลางยังทำงานและบูธเปิดรับ พร้อมแจ้งว่าสถานะอาจล่าช้าและรอฟังหน้าบูธ
- เครื่อง offline ยังไม่เห็นคิวใหม่ ลูกค้าแสดงหมายเลขจากระบบกลางให้สตาฟช่วยจัดลำดับ ห้ามสร้างหมายเลขอีกชุดมาชน
- ต้องมีวิธีบันทึก/กระทบยอดคิวใหม่ที่บริการไปแล้วแต่ยังไม่อยู่ใน cache ก่อนถือว่า offline flow ครบ
- พัก expiry อัตโนมัติของคิวเมื่อระบบตรวจพบเครื่องหลักขาดการเชื่อมต่อ ให้คนหน้างานตัดสินผู้ไม่มา
- เมื่อเชื่อมต่อกลับ ส่งรายการค้างและแก้ข้อขัดแย้งก่อนกลับโหมดปกติ ให้เวลาลูกค้าใหม่ ไม่หมดอายุย้อนหลังรวดเดียว
- การพักนี้ไม่กระทบ hold 15 นาทีของออเดอร์ออนไลน์

งานออกแบบทางเทคนิคที่ต้องปิดก่อน implementation: วิธีรู้ว่าเครื่องใดเป็นเครื่องหลัก; outage detection และระยะหน่วง; กรณี staff ยังออนไลน์แต่เครื่องหลักหลุด; การป้องกันหรือกักข้อขัดแย้งเมื่อหลายเครื่องออฟไลน์; stock ที่อาจถูกจองจากช่องทางอื่น; การกระทบยอดคิวที่ไม่อยู่ใน cache; ระยะผ่อนผันหลัง reconnect; revoked access ขณะ offline ไม่มีเครือข่าย ไม่สามารถสัญญาถอนสิทธิ์ทันทีได้

เกณฑ์ตรวจรับ: ทดสอบบนอุปกรณ์จริงตามสถานการณ์ข้างต้น พร้อมหลักฐาน reconciliation และข้อมูลก่อน/หลัง ห้ามประกาศ offline-ready จากการ cache หน้าเว็บอย่างเดียว ข้อจำกัดการล้างข้อมูลเครื่อง/ถอนการติดตั้งต้องอธิบาย และพิจารณาทางกู้รายการค้างที่เหมาะสม

## 7. แจ้งปัญหาออเดอร์

ลูกค้าเปิดลิงก์ออเดอร์เดิมเพื่อแจ้งประเภทปัญหา คำอธิบาย รูป และยืนยันช่องทางติดต่อ ร้านเห็นรายการและได้รับอีเมลแจ้งปัญหาใหม่ จากนั้นติดต่อพูดคุย ตรวจสอบ และตกลงแก้ปัญหาภายนอกระบบ

ร้านสามารถบันทึกปัญหาที่รับทางโซเชียลและผลการจัดการผูกกับ order เพื่อย้อนดูได้ เป็นทางเลือก ไม่บังคับ workflow ตอบกลับออนไลน์ ไม่มีระบบแชท การตัดสินจากภาพ หรืออนุมัติชดเชยอัตโนมัติในขอบเขตนี้

เกณฑ์ตรวจรับ: ผู้ไม่มีสิทธิ์เข้า order ไม่เห็นหลักฐานหรือส่งปัญหาแทน; จำกัด spam/จำนวนและขนาด upload; retry ไม่ส่งแจ้งเตือนซ้ำ; อีเมลล้มเหลวไม่ทำรายการแจ้งปัญหาหาย; ภาพปัญหาไม่เป็น public; ไม่ใส่ข้อมูลส่วนบุคคลเต็มใน notification

## 8. ภาพอัปโหลดและพื้นที่เก็บ

- รูปที่ผู้ใช้อัปโหลดทุกประเภท รวมรูปสินค้า โปรไฟล์ QR ชำระเงิน สลิป และรูปปัญหา ต้องแปลงเป็น WebP และย่ออย่างเหมาะสมก่อนส่ง พร้อมตรวจชนิดจริง ขนาด มิติ และจำนวนฝั่งรับข้อมูล
- สลิปต้องยังอ่านรายละเอียดและข้อมูลที่จำเป็นต่อการตรวจได้ชัด; ตรวจผลการแปลงก่อนใช้กับหลักฐานที่มีข้อกำหนดเก็บต้นฉบับ
- ใช้กลไกแปลงภาพ/ไลบรารีที่มีอยู่เมื่อเหมาะสม ไม่ต้องเพิ่มบริการภาพใหม่โดยไม่มีเหตุผล
- การแปลงล้มเหลวต้องแจ้ง ไม่อัปโหลดไฟล์ใหญ่เงียบ ๆ หรือแสดงสำเร็จปลอม
- ตั้งเพดานรูปต่อการแจ้งและไฟล์หลังแปลง ตัวเลขห้ารูปเคยเป็นข้อเสนอ ยังไม่ถือว่าได้รับยืนยันเฉพาะตัวเลข; ผู้พัฒนาตั้งค่าเริ่มต้นและบันทึกผลทดสอบคุณภาพ/ต้นทุนในตรวจรับ
- จัดการไฟล์กำพร้าจาก upload ที่ไม่ส่งฟอร์ม และลบตาม retention; signed access สำหรับหลักฐานสำคัญ
- ใช้ Supabase Storage เป็นที่เก็บและเรียกรูปเพียงบริการเดียว ยกเลิกการใช้ ImageKit ทุกจุด รวม preconnect; รองรับลิงก์รูปเก่าให้เรียกต้นทาง Supabase ได้โดยไม่ทำรูปเสีย หลักฐานส่วนตัวยังคงใช้ signed access ไม่เปลี่ยนเป็น public
- ตรวจ quota และค่า storage/egress/backup จริงก่อนสรุปค่าใช้จ่าย การถอดโค้ดไม่ใช่การยกเลิกแพ็กเกจ ImageKit ในบัญชี

## 9. ข้อมูลส่วนบุคคลและรายงาน

การตัดสินใจ: ที่อยู่จัดส่ง ช่องทางติดต่อ และรูปแจ้งปัญหาเก็บค่าเริ่มต้นหกเดือนหลังออเดอร์เสร็จสิ้น หากมีปัญหาค้างพักการลบ หกเดือนเป็นนโยบายบริการ ไม่ใช่ข้อสรุประยะตามกฎหมาย

การตัดสินใจเพิ่มเติม 13 กันยายน 2026: สลิปสำหรับบริการตรวจชำระเงินเก็บ 12 เดือนหลังออเดอร์เสร็จสิ้น พักการลบระหว่างข้อพิพาทและเหตุที่จำเป็นต้องเก็บหลักฐาน ให้ครีเอเตอร์ส่งออกหลักฐานได้ ระยะนี้เป็นนโยบายบริการ ไม่ใช่ข้อสรุปหน้าที่ตามกฎหมาย

สลิปและหลักฐานการเงินแยกตรวจหน้าที่บัญชี/ภาษีและข้อพิพาท ไม่ใช้กฎลบหกเดือนเหมารวม ก่อนเปิดต้องจัดทำตารางข้อมูล/วัตถุประสงค์/ผู้เข้าถึง/วันเริ่มนับ/วันลบ/ข้อยกเว้น รวม order ยกเลิกและไม่สำเร็จ บัญชีทีม และข้อมูลใน backup

เก็บประวัติสินค้า จำนวนขาย ราคา ส่วนลด promotion snapshot และสถิติคิวเพื่อให้ร้านวิเคราะห์งานย้อนหลังต่อได้ โดยตัดข้อมูลระบุตัวลูกค้าที่ไม่จำเป็น ไม่อ้างว่าลบชื่ออย่างเดียวทำให้ทุกข้อมูลนิรนาม และไม่รับปากเก็บตลอดไป

กำหนดช่องทางคำขอเข้าถึง แก้ไข ลบ/ส่งออกข้อมูล ตรวจตัวตนผู้ขอ และแจ้งผลหรือเหตุที่ต้องเก็บต่อ ปรับ Privacy/Terms/Cookies ให้ตรง implementation จริง พร้อมข้อกำหนดสถานะร้านปิด/ลบบัญชี การเผยแพร่เอกสารกฎหมายต้องตรวจตามข้อมูลและบริการจริง ไม่ใช้ spec เป็นคำรับรอง compliance

## 10. Monitoring และความยินยอม

ใช้ LogRocket session replay ได้เมื่อผู้ใช้ยินยอมก่อนเท่านั้น ผู้ไม่ยินยอมใช้ระบบหลักได้ตามปกติ ถอนความยินยอมได้ และหยุดการบันทึกในอนาคตจริง

ปกปิดข้อมูลลูกค้าบนหน้าเว็บ รูปสลิป/หลักฐาน ข้อความ และข้อมูลเครือข่าย รวม URL, headers, body, logs และ identity ที่อาจเผยข้อมูล ไม่ถือว่าปิด input อย่างเดียวเพียงพอ

เก็บข้อผิดพลาดทางเทคนิคเท่าที่จำเป็นแยกจาก replay พร้อมกรองข้อมูลและกำหนดสิทธิ์/อายุเก็บ ไม่สัญญาว่าจะส่งคลิปหรือแก้บั๊กอัตโนมัติหากยังไม่มี integration

เกณฑ์ตรวจรับ: ก่อนยินยอมไม่มี replay request; ปฏิเสธแล้ว workflow หลักทำงาน; consent เปลี่ยนมีผล; ตรวจ payload จริงและภาพ replay ว่าไม่มีข้อมูลต้องห้าม; alerts ที่จำเป็นต้องทดสอบส่งถึงผู้ดูแลจริง

## 13. Production gates และหลักฐานส่งมอบ

1. Functional: critical journeys ครบตั้งแต่สมัคร → ตั้งร้าน → ขาย/คิว/ส่งของ/คืนเงิน ตามบทบาทและช่องทาง
2. Security: auth/session/reset, RLS/grants/RPC/storage, cross-tenant และ public order lookup ผ่าน negative tests; ไม่มี secrets ใน client/log
3. Data integrity: concurrent last-item, hold expiry, duplicate clicks, stock adjustments, promotions และ refund/return ไม่สร้างยอดผิด
4. Offline: ผ่านสถานการณ์หัวข้อ 6 จริงบนมือถือ/แท็บเล็ต; มี reconciliation และข้อจำกัดที่ระบุชัด
5. Privacy: consent gating, retention exceptions, private evidence, data request process และข้อความนโยบายตรงของจริง
6. Reliability: API fail, reconnect, email/upload fail, app restart มี recovery ไม่มี fake success
7. Capacity: ทดสอบเพิ่มโหลดทีละระดับ ทั้งผู้ซื้อพร้อมกันและหลายบูธ รายงาน throughput, latency, error และความถูกต้อง ไม่ประกาศรองรับจำนวนคนก่อนมีผลทดลอง; กำหนดขอบเขตเปิดจากผลก่อน release
8. Backup: ยืนยัน backup มีจริงและ restore ได้ในสภาพแวดล้อมทดสอบ รวมฐานข้อมูลและไฟล์ Storage ที่จำเป็น ไม่สมมติว่า database backup ครอบคลุมไฟล์; บันทึกเวลาที่ใช้และขอบเขตข้อมูลที่อาจสูญเสีย
9. Deployment: staging/prod แยก ตรวจ migration history จริง CI ผ่าน env ถูกต้อง มี rollback/update procedure ไม่ทับรายการ offline ค้าง
10. UX/PWA: ติดตั้ง เปิดจาก icon สลับแอป login deep link upload keyboard safe area update และทั้งสองภาษา ผ่านอุปกรณ์เป้าหมายจริง

หลักฐานต่อข้อ: scenario, environment/version, วิธีทดสอบ, expected/actual, ผลผ่าน/ไม่ผ่าน และข้อจำกัด ห้ามนับ test ที่ skip เป็นผ่าน ต้องแก้ข้อผิดพลาดที่ทำเงิน/ข้อมูล/สิทธิ์/ลำดับคิวเสียก่อนเปิด ไม่ deploy production โดยอาศัยภาพต้นแบบหรือ build ผ่านอย่างเดียว

## 14. ลำดับดำเนินงานและนิยามเสร็จ

เริ่มจากตรวจ source กับสเปกและจัดช่องว่าง ใช้ tests เดิมก่อนเพิ่ม; ปิดแบบ offline/permissions/retention ที่กระทบข้อมูล; ทำต้นแบบกดได้ตาม visual direction และทดสอบบนเครื่องจริง; พัฒนาเป็นชุดงานที่เชื่อมกัน; รัน gates และแนบหลักฐานเปิดใช้งาน

ไม่จำเป็นต้องถามผู้ใช้เรื่อง implementation ย่อย ให้เสนอ/เลือกค่าเริ่มต้นพร้อมเหตุผลและทดสอบเอง ถ้าพบผลกระทบต่อความเป็นธรรมของคิว เงิน ข้อมูลลูกค้า หรือ workflow ที่ขัดการตัดสินใจนี้ จึงนำทางเลือกที่เป็นรูปธรรมกลับมาถาม

นิยามส่งมอบ: ขอบเขต v1 ทำงานครบทั้ง UI/server; สิทธิ์และข้อมูลถูกต้อง; ภาษาและหน้าจอสอดคล้อง; tests สำคัญผ่าน; offline recovery พิสูจน์ได้; ผู้ใช้ตรวจรับต้นแบบใช้งานจริง; บันทึกความเสี่ยง/ข้อจำกัดและคู่มือเปิดใช้งาน ไม่มีการ commit/push/deploy โดยอัตโนมัติจากเอกสารฉบับนี้
