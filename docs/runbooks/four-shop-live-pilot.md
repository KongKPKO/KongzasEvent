# Pilot NireQ: ใช้จริง 3–4 ร้านในงานเดียวกัน

อัปเดต 12 ตุลาคม 2026 (Asia/Bangkok)

เป้าหมายคือใช้เว็บออนไลน์ในงานจริง โดยแต่ละร้านเตรียมสินค้าและมีวิธีขาย/บัตรคิวปกติสำรอง ผู้ดูแลสังกัดช่วยประสานงานและดูการทดลองของแต่ละคนได้ โดยรอบนี้ไม่สร้าง dashboard รวมสังกัดหรือ kiosk คิว merchandise กับ cheki/ถ่ายภาพคงเป็นคิวรวม

## ขอบเขตรอบแรก

- 4 ร้าน = 4 owner/workspace แยกกัน แต่ละร้านมี URL, event, catalog, allocation, team และยอดขายของตัวเอง ไม่ใช่ 4 events ใต้ร้านเดียว
- ใช้ event-first workspace เดิม ตั้ง event ชื่องานเดียวกันได้ แต่รายละเอียดบูธและวันเวลาเป็นของร้านนั้น
- เริ่มด้วยหน้าร้าน/เมนู คิวรวม POS และการรับเงินที่ทีมงานตรวจเอง การโอน/PromptPay ไม่ได้มีระบบตรวจยอดธนาคารอัตโนมัติ
- Pre-order เพิ่มในร้านที่ซ้อมส่งสลิป/reject/resubmit/confirm/pickupผ่านก่อนงาน อย่าเปิด Campaign หรือ post-order เพียงเพราะมีฟีเจอร์ ถ้าไม่มีคนรับผิดชอบ fulfilment
- บทบาทตัวอย่างต่อร้าน: ownerเตรียมของ + sellerขาย/ตรวจเงิน + queue_staffเรียกคิว ถ้าทีมเล็กคนเดียวอาจทำหลายหน้าที่ตามสิทธิ์ที่ได้รับ
- เจ้าของ NireQ อยู่ช่วยสังเกตและรับปัญหา ผู้ดูแลสังกัดประสานร้านต่าง ๆ และดูหน้าร้านลูกค้าของแต่ละคนผ่านURLแยกได้ โดยไม่แชร์รหัสผ่าน owner ข้ามร้าน
- ไม่รับปากว่าบัญชีmanagerหนึ่งบัญชีสลับหน้าจัดการครบ4ร้านได้: actor contextปัจจุบันเลือกร้านเดียว ไม่มีworkspace switcher ถ้าต้องช่วยจัดการหลายร้านให้ตกลงวิธีเข้าร้านตามสิทธิ์ที่รองรับก่อน รัน4ร้านพร้อมกันครั้งนี้ใช้4ownerแยกบัญชี

## ก่อนงาน

1. ระบุงาน/วันที่/รายชื่อ 3–4 ร้าน/อุปกรณ์ของทีมและช่องทางติดต่อ กำหนดว่าจะใช้เงินจริงใน deployment ไหน การนำโค้ดขึ้นเว็บหรือเปลี่ยนข้อมูล live ต้องได้รับอนุมัติ target/actionก่อน
2. แต่ละ ownerสมัครและยืนยันอีเมลเอง ตั้งร้านและติดต่อ สร้างevent วันเวลา/เขตเวลา สถานที่ จุดคิว และรายละเอียดบูธให้ครบ
3. ตั้งสินค้า ราคา และ variant/SKU; นับของจริงแล้วบันทึก recorded total; จัดสรร stockให้event ตรวจว่า online displayตรงกับของที่เอาไปงาน
4. ตั้ง payment instructionของร้านนั้นเอง เชิญทีมด้วยemailของเจ้าตัว ตรวจว่า seller/queue_staffเลือกeventและเห็นเฉพาะหน้าที่ที่ต้องใช้
5. Publish/previewตามเงื่อนไขจริง ตรวจ URLและQRของแต่ละร้านแยกกัน ห้ามเอา URL ร้านหนึ่งติดอีกบูธ
6. ซ้อมบน deployment ที่จะใช้จริง ด้วยเจ้าหน้าที่และมือถือจริงของทั้ง4ร้านพร้อมกัน: login, รับคิว, เรียก/arrived, cash, manual transfer confirmation, receipt/history/stock และหยุด/เปิดบูธ การทดสอบในเครื่องไม่รับรองเน็ตในงานหรือdeployment parity
7. เตรียมบัตรคิวกระดาษแยกร้าน สมุดขาย/ไฟล์จด ราคาและสต็อกฉบับออฟไลน์ เครื่องคิดเลข หลักฐานรับเงิน และแบตสำรอง

## วันงาน

- ก่อนเปิด: ownerแต่ละร้านตรวจevent/Booth Open, สินค้า/ราคา/ยอดพร้อมขาย และช่องทางรับเงิน sellerทดลองดูPOS queue_staffทดลองดูคิว
- เริ่มพร้อมกันทั้ง4ร้าน เก็บเวลาและรหัสร้านในบันทึกปัญหา อย่ารวมเลขคิวข้ามร้าน
- ทดสอบช่วงที่มีคนจริงแต่ยังควบคุมได้ก่อน จดจำนวนorderสำเร็จ ปัญหาคิว เวลาต่อรายการ และจำนวนครั้งที่ใช้วิธีสำรอง ไม่อ้างว่าลดเวลาขายจนกว่าจะวัดได้
- ทุกช่วงพัก กระทบยอดordercompletedกับเงินสด/เงินเข้าที่ร้านตรวจ และดู stock_sold/reserved ของeventนั้น
- การ timeout หลัง Charge หรือ Confirm อาจเกิดหลังฐานข้อมูลบันทึกแล้ว: ตรวจสถานะorder/historyและหลักฐานเงินก่อนกดซ้ำ ไม่สรุปว่าขายไม่สำเร็จเพียงเพราะหน้าจอค้าง

## เมื่อสลับไปวิธีสำรอง

1. แต่ละร้านกำหนดคนตัดสินใจและบันทึกเวลาสลับ ไม่ปล่อยให้พนักงานบางคนขายในเว็บและบางคนจดกระดาษโดยไม่รู้กัน
2. ถ้าเว็บเข้าถึงได้ ให้หยุดรับคิว/ขายใหม่ในช่องทางที่เกี่ยวข้อง และยืนยันผลบนหน้าลูกค้า การกดปิดแต่ไม่มีผลตอบกลับไม่ถือว่าปิดสำเร็จ
3. จดคิวออนไลน์ที่รอและกำลังเรียกไว้ก่อน แจกบัตรกระดาษด้วย prefix ต่างจากเลขออนไลน์ เช่นร้านAใช้ A-P001 เพื่อไม่เรียกเลขซ้ำ จัดลำดับต่อจากคิวเดิมโดยมีคนดูแล
4. สำรองสมุดขายแยกร้าน: เวลา รหัสใบขาย สินค้า/variant จำนวน ราคา วิธีชำระ และใครตรวจเงิน ไม่จดข้อมูลลูกค้าเกินจำเป็น
5. สินค้าที่ขายกระดาษต้องไม่ทับกับยอดที่ออนไลน์ยังขายหรือholdอยู่ หากยืนยันปิดออนไลน์ไม่ได้ ให้ใช้ส่วน stockสำรองที่กันไว้นอกallocation หรือหยุดขายสินค้าที่อาจชนจนตรวจยอดได้
6. เมื่อระบบกลับมา กระทบยอดรายการก่อน timeoutก่อน รายการที่มีorderสำเร็จแล้วไม่checkoutซ้ำ รายการกระดาษต้องมีคนตรวจและเลือกวิธีนำเข้าประวัติ/ปรับstockตามความสามารถระบบจริง ไม่ถือว่าระบบซิงก์ออฟไลน์ให้อัตโนมัติ

## หลังงาน

แต่ละร้านนับของเหลือ ตรวจออเดอร์ค้าง/hold/รับสินค้า และกระทบยอดเงิน ยอดจากวิธีสำรองรายงานแยกจากยอดระบบจนปรับให้ตรง มีผู้รับผิดชอบ fulfilmentต่อหลังปิดงาน ผู้ดูแลสังกัดรวบรวมข้อสังเกตจากทั้ง4ร้านในเอกสารร่วมได้ โดยรอบนี้ไม่ต้องมีdashboardรวม

## หลักฐานการตรวจและข้อจำกัด

- 12 ต.ค. ซ้อมขายครบ 4 ร้านพร้อมกันผ่านฐานข้อมูลจริงในชุด local แยก: 4 browser processes, 8 sessions (4 owner + 4 customer) เตรียม fixture ด้วยเครื่องมือทดสอบ ไม่ใช่เจ้าของ 4 ร้านสมัครและเตรียมสินค้าเองครบทั้งชุด
- ผ่าน login และ cold reload พร้อมกัน, ลูกค้ารับคิว, Call Next, ARRIVED, เลือกสินค้า, จ่าย cash, คิว complete; ตรวจยอดขาย 101–104 บาทตามร้าน สต็อก sold เพิ่มร้านละ 1 และ reserved กลับเป็น 0
- ตรวจ owner อ่าน order ร้านอื่นไม่ได้, เปลี่ยน event ร้านอื่นไม่ได้ และ anonymous อ่าน order ส่วนตัวไม่ได้
- Preorder ผ่าน customer order, ส่งหลักฐานทดสอบ, reject/resubmit/confirm และ pickup ใน local โดยไม่มีเงินจริง
- แก้ account/workspace/event load ล้มเหลวให้แสดง error/retry แทนการสรุปว่าออกจากระบบ ไม่มีสิทธิ์ หรือร้านปิด; ป้องกัน response เก่าทับข้อมูลใหม่ การ retry อ่านข้อมูลไม่ replay Charge/Confirm
- แก้ปุ่มสินค้า POS ให้รอโหลดออร์เดอร์เสร็จก่อนกด พร้อมแสดงสถานะ disabled ชัดเจน เพราะก่อนหน้านี้กดระหว่างโหลดแล้วไม่เพิ่มสินค้า
- ทดสอบการกู้คืนหลัง 504, membership lookup failure, invitation/admin lookup failure, token ถูกปฏิเสธ และการต่ออายุ session สะดุด; ไม่ผ่อน RLS หรือใส่ privileged key ใน browser
- `npm run verify` ใน working checkout ผ่าน: lint/build, SQL 20 suites / 439 assertions, stock concurrency 5 รอบ, browser 73 tests และ API smoke 8 checks
- ชุด release ที่ตัดงาน catalog/appearance ออก ตรวจ `npm run verify` ผ่านอีกครั้ง: browser 56 tests, SQL 439 assertions, stock concurrency 5 รอบ และ API smoke 8 checks; ตัวทดสอบ catalog ใช้ชื่อปุ่มและช่องกรอกที่มีจริงในรุ่นเดิม
- local PostgreSQL image เดิมมี pgTAP crash จึงเปลี่ยนเฉพาะชุดทดสอบแยกเป็น 17.6.1.155; ไม่เปลี่ยนฐานข้อมูลออนไลน์
- ผู้ใช้อนุญาตหยุด local อีก 4 ชุดชั่วคราว: NireqDevProductValidation, NireqVariantValidationStable, NireqBetaValidation และ EventWebQueue เก็บรายการ 40 containers เพื่อเปิดคืนตามเดิม เมื่อหยุดแล้วการทดสอบ 4 ร้านขายจบได้; ปัญหา runtime ก่อนหน้ามีหลักฐาน memory pressure/DB timeout
- ชุด frontend สำหรับ release แยกเฉพาะ auth/retry และ POS loading guard พร้อม tests; ไม่รวม feature catalog/appearance หรือ migration ที่ยังเป็นงานอื่นใน working tree เป้าหมายเว็บที่ได้รับอนุญาตคือ https://nireqapp.com
- ผลนี้ไม่ใช่ load test จำนวนลูกค้ามาก ไม่รับรองเน็ตในงาน และไม่ได้ใช้เงินจริงบน production ต้องซ้อมด้วยมือถือ/ทีมจริงบน deployment ที่จะใช้ก่อนเปิดงานตามขั้นตอนด้านบน
