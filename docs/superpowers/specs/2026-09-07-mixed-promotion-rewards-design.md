# เลือกของแถมคละและยืนยันรับไม่ครบสิทธิ์

## ขอบเขตที่ตกลง

แก้ข้อบกพร่องของ Promotion reward selection ใน Online Campaign, Event Pre-order/Post-order และ live POS โดยใช้ระบบราคาและการจอง/ขายเดิม ไม่เปลี่ยนสูตรส่วนลดหรือวิธีตัดสินโปรชนกัน

ลูกค้าได้สิทธิ์ 2 ชิ้นและ A/B เหลืออย่างละ 1 ต้องเลือก A1+B1 ได้ หากเหลือรวมเพียง 1 ให้เลือกรับ 1 พร้อมคำเตือนและการยืนยันชัดเจน ห้ามลดจำนวนของแถมเงียบ ๆ

## กติกา

| สถานการณ์ | ผลลัพธ์ |
|---|---|
| ได้ 2; A1+B1 | เลือกคละได้รวม 2 |
| ได้ 2; A2+B1 | เลือก A2 หรือ A1+B1 ได้ แต่ B2 ไม่ได้ |
| ได้ 2; A1+B0 | แจ้ง «ของแถมเหลือไม่ครบสิทธิ์: ได้สิทธิ์ 2 ชิ้น เหลือให้รับ 1 ชิ้น» ต้องยืนยันรับ 1 |
| ได้ 2; ทุกแบบหมด | ใช้ flow เดิม: แจ้งหมดทั้งหมด แสดงยอดใหม่ และยืนยันซื้อโดยไม่มีโปรของแถมนั้น |
| ของแถมแบบร้านกำหนด เหลือพอ | รับอัตโนมัติตามเดิม |
| ของแถมแบบร้านกำหนด เหลือไม่ครบ | ต้องยืนยันรับจำนวนที่เหลือเช่นเดียวกัน ไม่แถมบางส่วนอัตโนมัติ |
| ของแถมไม่จำกัดจำนวน | ไม่จำกัดด้วย stock counter แต่ยังจำกัดด้วยสิทธิ์ที่ได้รับ |

ใช้กติกาเดียวกันกับ quantity gift และของแถมแต่ละ spend tier จำนวนสิทธิ์ยังคำนวณจากกติกาเดิม

## UI

- แสดงแต่ละของแถมพร้อมจำนวนคงเหลือ ปุ่มลด/เพิ่มจำนวน และยอด «เลือกแล้ว X/Y ชิ้น»
- ยืนยันได้เมื่อเลือกรวมครบจำนวนที่รับได้และไม่เกินแต่ละ SKU
- ถ้ารับไม่ครบสิทธิ์ แสดงคำเตือนและปุ่ม «ยืนยันรับของแถม 1 จาก 2 ชิ้น» ไม่ใช้ข้อความทั่วไปที่มองข้ามเงื่อนไขได้
- ใช้ component เดียวร่วมกันทั้งสามหน้าจอ เพื่อให้กติกาและข้อความตรงกัน รองรับ TH/EN และปุ่มที่เข้าถึงได้ด้วยคีย์บอร์ด
- ส่งตัวเลือกไปคำนวณราคาใหม่หลังยืนยันการเลือก ไม่ส่งทุกครั้งที่กดเพิ่มจนแบบฟอร์มหายระหว่างเลือก

## Backend และความปลอดภัย

- ตัวเลือกของแถมต้องรวม SKU ที่เหลืออย่างน้อย 1 ชิ้น ไม่กรองทิ้งเพียงเพราะ SKU เดียวมีไม่ครบสิทธิ์ทั้งหมด
- Resolver ตรวจจำนวนรวมและจำนวนต่อ SKU จาก stock ฝั่ง server; payload ที่เลือกเกิน/เลือกรายการนอกโปรต้องไม่ผ่าน
- Partial acceptance ระบุจำนวนที่ยอมรับอย่างชัดเจนใน reward choice ไม่อนุมานว่าการเลือกไม่ครบคือยอมรับแล้ว
- หาก stock เปลี่ยนจนจำนวนที่รับได้ต่างจากตอนยืนยัน ต้องขอเลือก/ยืนยันใหม่ ไม่ใช้การยอมรับครั้งเก่ากับข้อเสนอใหม่
- เก็บข้อมูลสิทธิ์และจำนวนที่ยอมรับใน pricing snapshot ของออเดอร์ โดยไม่เพิ่มตารางใหม่
- ใช้ transaction/row locks ใน checkout เดิม ตรวจของซื้อและของแถมรวมกันก่อนสำเร็จ; ถ้าของไม่พอต้อง rollback ทั้งออเดอร์
- Hold 15 นาทีสำหรับ Online/Pre/Post และการขายทันทีสำหรับ live POS เหมือนเดิม

## ไฟล์และแนวทาง

- Migration ใหม่แก้ `private.promotion_reward_options`, `private.resolve_promotion_rewards` และ metadata ของ required choices ใน calculator ไม่แก้ migration เก่า
- เพิ่ม shared reward picker ภายใต้ `src/components/promotions/`
- เชื่อม picker ใน `OnlineCampaignStorefront.tsx`, `MenuView.tsx`, `PosPanel.tsx`
- ขยาย `src/types/promotion.ts` สำหรับจำนวนที่รับได้และ partial acceptance

## การทดสอบ

1. SQL: A1+B1 เมื่อได้ 2 ต้องผ่าน; A2 เมื่อเหลือ A1 ต้องไม่ผ่าน
2. SQL: เหลือรวม 1 เมื่อได้ 2 ต้องรอ partial acceptance; ไม่มี acknowledgment ต้องไม่ resolve
3. SQL: stock เปลี่ยนหลังยืนยันต้องไม่ให้ของแถมน้อยลงเงียบ ๆ
4. SQL: fixed gift, quantity gift, spend tier และ unlimited ยังถูกต้อง
5. Integration: จองของซื้อ+แถม, expiry คืน stock และ live sale ไม่สร้าง hold
6. Browser: เลือกคละ, เลือกไม่ครบปุ่มปิด, ยืนยัน partial และข้อความหมดจริง บน desktop/mobile
7. รัน narrow tests, `npm run verify`, review diff และ regression ที่เกี่ยวข้องก่อนส่งมอบ

## ไม่รวม

ไม่เปลี่ยนสูตรส่วนลด ไม่เพิ่ม promo codes ไม่ปรับหน้าร้านนอกส่วนของแถม และไม่ deploy DEV/PROD โดยอัตโนมัติ
